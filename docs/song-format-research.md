# ChordPro чи ChordMark для «Збірника»

Дата перевірки: 28 жовтня 2026 року, до реалізації сіток у версії 1.1.0.

Це історичний звіт. Поточну підтримку описано в [документації сіток і бою](chordpro-grids.md).

## Висновок

Залишити ChordPro основним форматом пісні. Розширити його підтримку стандартними сітками акордів і схемами бою.

ChordMark краще моделює тривалість акордів разом із позиціями у словах. Проте його готова бібліотека не є прямою заміною нашого парсера.

Обидва проєкти підтримуються. Вибір ChordPro не означає, що ChordMark покинутий або непридатний.

Переглянути рішення, якщо точна ритмічна послідовність стане основною моделлю всього редактора. Для поточного пісенника повна міграція не виправдана.

## Порівняння можливостей

| Потреба | ChordPro | ChordMark |
| --- | --- | --- |
| Текст і акорди над словами | Прямий запис `[Am]слово` | Окремий рядок акордів і маркери `_` у тексті |
| Тривалість акорду | Сітка задає розміщення в комірках; звичайний тег акорду не задає тривалість | Явні тривалості, позиції долей і дробові групи |
| Ритмічна сітка без слів | Стандартні `start_of_grid` / `end_of_grid` | Генерується з тієї самої моделі, що й текст з акордами |
| Схема бою | Стандартні рядки Strums: напрямок, акцент, глушіння тощо | Аналога стандартних ChordPro Strums у перевіреній документації не знайдено |
| Повтори | Повтори тактів у сітках; повтор приспіву; є експериментальне запам’ятовування акордів | Повтори тактів, рядків і секцій; автоматичне повторення акордів |
| Метадані пісні | Директиви; частина наших полів є власними розширеннями | Готовий конвертер не переносить наш набір метаданих |
| Обмін з іншими пісенниками | Зрілий формат; підтверджено підтримку, зокрема сіток, у LinkeSOFT SongBook | Є конвертери, але вони не забезпечують збереження всіх даних |
| Нативний Expo-інтерфейс | Уже є власний TypeScript-парсер і React Native-компоненти | Стандартне відображення — HTML; навіть парсер залежить від DOM |

Підтримка ChordPro в іншій програмі не гарантує підтримку всіх директив. Сітки, Strums і розширення потрібно перевіряти окремо.

### Що означає ритмічна сітка ChordPro

```chordpro
{start_of_grid shape="2x4"}
| Am . . . | F . G . |
{end_of_grid}
```

Це два такти по чотири комірки. `.` означає порожню комірку, а не формальну команду продовжувати звук.

Документація також визначає `/`, кілька акордів через `~`, повтори тактів та Strums. Цього достатньо для багатьох статичних репетиційних схем.

Для відтворення потрібно окремо визначити тривалість комірки, початок відліку, повтори й інтерпретацію порожніх комірок.

ChordPro має механізм `cc` і `[^]`, який пов’язує сітки з послідовністю акордів у тексті. Офіційна документація позначає його експериментальним.

Не варто робити цей механізм обов’язковим для обміну піснями. Він також не надає автоматичного вирівнювання слів за аудіозаписом.

### Де ChordMark сильніший

```text
4/4
#v
Am... G.
_Слава _Богу
```

У цьому прикладі `Am` триває три долі, `G` — одну. Маркери `_` задають позиції змін акордів у словах.

Парсер повертає окремі значення `duration` і `beat`. Це зручніше для майбутнього підсвічування акордів, ніж аналіз геометрії сітки.

Документація також визначає дробові групи, зміну розміру та поділ такту між рядками. Наявність цих даних не замінює аудіорушій.

## Результати ізольованих проб

Використано Node.js 24 і пакети `chord-mark`, `chord-mark-converters`, `chord-mark-jsdom` версії `0.18.0`.

Скрипт із перевірками збережено локально: `/tmp/songbook-format-research.G0zYiq/probe.cjs`. Тимчасовий каталог не входить у репозиторій.

| Проба | Результат |
| --- | --- |
| `Am... G.` у 4/4 | Тривалості `[3, 1]`, початки `[1, 4]` |
| Український текст із `_` | Текст і позиції акордів розпізнано |
| `C.. G. [Am F]` | Тривалості `[2, 1, 0.5, 0.5]` |
| `6/8` і `Am. G.` | Дві долі в такті, по одній на акорд |
| Основний парсер без DOM | Помилка `sanitize is not a function`, навіть після надання глобального `self` |
| Той самий парсер через `chord-mark-jsdom` | Працює в Node.js |
| ChordPro → ChordMark | Втрачаються метадані, зокрема заданий розмір `3/4`; результат інтерпретується як 4/4 |
| ChordMark → ChordPro | Нерівні тривалості виходять як `[Am...]` і `[G.]`, а не стандартна сітка |
| Некоректна сума `Am... G..` у 4/4 | Рядок стає текстом, виняток не виникає |
| Приклад API з README конвертерів | `chordMarkToChordPro` відсутній; фактичний експорт — `chordMark2ChordPro` |

### Ризик автоматичної конвертації

Вхідна проба містить назву, тональність, темп, розмір, капо, теги, бій, посилання й заголовок куплету.

Готовий конвертер повертає:

```text
#Куплет

#v
Am G
_Слава _Богу
```

Він не переносить метадані та змінює структуру заголовка. Без явних тривалостей ChordMark вважає кожен акорд цілим тактом.

Це значення за замовчуванням формату, а не відновлений ритм оригінальної пісні. З позицій акордів у словах неможливо надійно визначити тривалість.

Наш поточний парсер читає `[Am...]` як назву акорду `Am...`. Він не отримує з цього тривалість три долі.

Отже, готові конвертери не можна застосувати до всього каталогу без власного перенесення метаданих і перевірок втрат.

### Інтеграція з Expo

У `parseSong` ChordMark кожен рядок проходить через DOMPurify. Це стосується не лише HTML-відображення, а й парсера.

`chord-mark-jsdom` вирішує проблему для Node.js, але не є готовим рішенням для React Native/Hermes.

Для нативної інтеграції потрібно перевірити можливість відокремлення парсера від DOM і створити відображення через наші компоненти.

WebView є окремим варіантом, але його доступність, масштабування, виділення тексту й поведінку потрібно оцінювати окремо.

### Розмір 6/8 і метроном

ChordMark повертає для 6/8 дві долі. Наш `beatGrid('6/8')` створює шість позицій, із наголосами на першій і четвертій.

Пряме поєднання цих лічильників із тим самим BPM дасть неправильне співвідношення часу. Потрібно явно визначити одиницю темпу та підподіл.

Це питання потрібно вирішити незалежно від вибраного формату.

## Що реально підтримує наш код

Наш парсер поки не підтримує ChordPro повністю.

- `packages/shared/src/chordpro.ts`: немає моделі сіток, схем бою, початку й тривалості акорду.
- `parseDirective` не розпізнає атрибути на кшталт `shape="2x4"`.
- Проба сітки повертає порожній список акордів. Рядок сітки й директива з атрибутами потрапляють у звичайний текст.
- `chordBars` ділить простий рядок на такти для показу. Це не повна ритмічна модель.
- `apps/mobile/src/lib/song-builder.ts`: візуальні блоки побудовано на коментарях із назвами частин пісні.
- `apps/mobile/src/components/metronome.tsx`: програє один такт у циклі, а не послідовність усієї пісні.

Поле `chordpro` використовується в API, пропозиціях, SQLite, синхронізації, знімках поширення, PDF та імпортері нотаток.

Повна заміна формату зачіпає всі ці шляхи. Потрібна сумісність зі старими клієнтами й уже створеними знімками.

## Рекомендований порядок роботи

1. Задокументувати підтримувану підмножину ChordPro та відокремити власні директиви від стандартних.
2. Додати коректне читання атрибутів і збереження невідомого синтаксису без втрат.
3. Додати стандартні сітки акордів: редактор, нативний показ, транспонування та PDF.
4. Додати Strums без зміни звичайного режиму читання пісні.
5. Перед підсвічуванням визначити тривалості, паузи, повтори, одиницю BPM і поведінку 6/8.
6. Перевірити це на кількох реальних піснях із нерівними тривалостями та програшами.
7. Повернутися до ChordMark, якщо постійна прив’язка тривалостей до слів стане головною вимогою.

Не підтримувати два незалежні редаговані оригінали однієї пісні. Це створить ризик розходження даних.

Жоден із форматів не визначає ритм автоматично з тексту чи аудіозапису. Невідому тривалість потрібно позначати як невідому.
