# Ручна перевірка функцій

Це критерії приймання, а не звіт про реалізацію або успішне тестування. Виконуйте їх після завершення відповідних змін. Позначте кожен випадок як пройдений, непройдений або заблокований і запишіть версію збірки, пристрій та результат. Перевірте також [регресійні сценарії UX](ux-fixes.md).

## Підготовка

- Використайте тестове середовище, два пристрої або акаунти з потрібними ролями та тестові пісні. Не використовуйте приватні дані громади.
- На обох платформах перевірте встановлену збірку, а не лише Expo Go. Спочатку дочекайтеся синхронізації пісень.
- Для кожної функції перевірте українські підписи, доступність озвучуванням, великий текст і відмову в системних дозволах. Дія має бути зрозумілою, а дані не мають зникати без попередження.

## Міграції, офлайн і приватність

1. Встановіть попередню збірку з копією тестових даних. Створіть локальний альбом і змініть локальний текст, транспонування та капо. Оновіть збірку без видалення застосунку. Очікування: пісні, локальні зміни, альбоми й порядок збережені; повторний запуск не дублює записи.
2. Після початкової синхронізації вимкніть мережу. Відкрийте завантажені пісні й локальні дані та виконайте підтримувані локальні зміни. Очікування: доступний вміст читається, зміни переживають перезапуск, мережеві дії не видають помилковий успіх.
3. Поверніть мережу та синхронізуйте. Очікування: локальні дані не втрачені; серверні зміни оновлюються без дублікатів. Перевірте окремо конфлікт версій і переривання синхронізації: користувач бачить помилку або конфлікт, повтор не втрачає дані.
4. Перевірте вихід і зміну акаунта, а також відмову сервера 401/403. Очікування: приватні дані попереднього акаунта недоступні іншому; користувач розуміє, які локальні дані залишаються. Не припускайте, що неавторизоване очищення спільного кешу зберігає незбережені зміни.
5. Перевірте QR, PDF, системне поширення, логи та мережеві запити на тестових даних. Очікування: токени входу, особисті нотатки й аудіо не потрапляють до вихідних матеріалів без необхідності та явної згоди.

## EAS Build і Submit: перевірка перед випуском

- Перевірте ідентифікатори застосунку, версію, номер збірки, дозволи, іконки та сторінки конфіденційності для обох магазинів.
- Переконайтеся, що production API використовує `DEV_MODE=false`, окремі production-ресурси та реальну доставку пошти. Не використовуйте dev-коди входу чи тестову авторизацію в production.
- Зберігайте серверні секрети тільки в сховищі секретів сервера. Не додавайте їх у репозиторій, `EXPO_PUBLIC_*`, мобільну збірку, журнали або матеріали для магазину. Публічна адреса API не є секретом.
- Production-профіль EAS і iOS ASC ID налаштовано. iOS-збірка 1.0.0 (5) та Submit завершені; див. [звіт перевірок](release-checks.md). Перевірте облікові дані Android і підписування. Встановіть production-збірки на iOS і Android через внутрішнє тестування.
- У встановлених збірках перевірте запуск, вхід без dev-авторизації, синхронізацію, офлайн-читання, перехід за посиланням і критичні сценарії з матриці. Перевірте дозволи й повідомлення про помилки.
- Після успішного smoke-тесту перевірте обрані артефакти та метадані в EAS Submit. Надсилайте їх лише за окремим дозволом на випуск; отримання збірки магазином не означає її публікацію.
